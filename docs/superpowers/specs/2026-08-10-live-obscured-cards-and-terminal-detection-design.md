# 遮挡出牌、简明对局日志与自动封存设计

## 目标

修复实时助手在腾讯大掼蛋界面上遇到遮挡牌和结算页时的四个问题：

1. 出牌区点数已识别但花色被动画或按钮遮挡时，仍必须按真实张数推进对局，不能把少牌结果提交给 DanZero。
2. 对局动态以每条事件一行的简明文字显示，例如“第 1 手　左家出牌：33445?7”，不再将牌面拆到下一行或渲染为大卡片表格。
3. 头游、二游、三游、末游和接风继续由已确认动作的张数与轮次推导；花色不确定不能影响剩余张数和生命周期事件。
4. 结算页出现“再来一局”或“换桌”时，必须从底部结算按钮区检测并自动封存当前 session，随后恢复下一局监听。

## 已确认的根因

最新 session `game_20260810_000418_3ccf81` 的首手录像第 72/73 帧显示左家六张牌。视觉日志连续记录“5 未匹配到花色”，但两帧策略仍将五张 `3H 3S 4D 4S 7H` 作为合法牌型提交。遗漏的一张 5 被界面层遮住了花色；当前 live 路径没有启用 `allow_unknown_suit`，且“两次有效牌型一致”只校验提交后的完整花色编码。

同一录像的末帧有“换桌”和“再来一局”，位置在底部 `y≈600`。现有快速信号只扫描中部 `button_actions` 区域（`y=210..360`），所以从未发布 `game_end_detected`，控制器也就不会调用 `finish()`。

生命周期事件缺失不仅是首手少一张：该 session 只确认了极少数动作，没有任何座位的剩余张数变为零。首手少牌会让该座位永远少扣一张；一旦错误花色导致后续“双副牌超过两张”校验拒绝动作，偏差会进一步扩大。

## 设计原则

- **张数事实与花色推断分离。** `8?` 表示“点数 8 已确认、花色未知”，它是正式动作证据而不是失败或默认花色。
- **不将猜测写成事实。** 任何未知花色只保存在事件的候选花色元数据中；后续清晰帧可缩小候选，不能把 `8?` 的历史改写成伪造的 `8S`。
- **策略输入可以暂时具体化，状态历史不可以。** DanZero 需要具体花色，故只在生成策略副本时枚举符合颜色、双副牌库存和牌型的分配；原 reducer、时间线和 session 日志仍保存未知牌。
- **建议可降级但流程不断。** 所有可行分配给出相同建议时显示常规建议；不同分配得到不同建议时显示“花色推断，低置信”及候选，不暂停回合、不丢失动作。
- **约束必须单调收紧。** 新的精确观测只能排除花色候选。若先前策略副本的临时分配不再可行，旧建议置为 stale 并重新计算，不改变已确认张数、回合或游次。

## 数据与状态边界

### 识别结果

`PlayRegionResult` 和 `RecognitionSample` 新增与 `cards` 等长的花色候选信息。完整牌使用单元素候选（例如 `("S",)`）；遮挡牌使用颜色受限候选（红色为 `("H", "D")`，黑色为 `("S", "C")`）。若颜色也无法可靠判定，则使用四花色候选。视觉输出仍以 `5?` 表示未知花色。

### 共识、Reducer 与日志

共识对“点数序列 + 花色候选集合”投票，防止同为 `8?`、但颜色证据不同的帧被混为同一个候选。动作合法性以所有可能的具体花色分配进行检验：至少存在一个同时满足双副牌、当前牌型和压牌规则的分配才接受；仅在某个幸运花色下才成立的百搭/同花顺不作为高置信结论。

`LiveEvent.payload` 保存 `cards` 与 `unknown_suits`（按卡牌位置记录候选）。Reducer 按 `len(cards)` 扣减剩余牌数，故 `8?` 对头游、接风和轮转与完整牌等价。精确双副牌校验由可行分配检查代替“把问号当单独牌码计数”。

### DanZero 策略副本

创建策略请求时，对 reducer 的不可变状态生成所有可行、去重的具体花色副本；小规模组合穷举并设置上限。每个副本独立调用现有 DanZero 适配器。

- 所有副本产生同一 `cards/is_pass/play_type`：发布该建议，标注 `suit_resolution="consistent"`。
- 副本结果不同：按出现次数选择代表建议，保留全部不同建议与覆盖数，标注 `suit_resolution="ambiguous"` 与低置信。页面和 `advice.jsonl` 必须说明“花色推断”。
- 解析失败的副本单独记录，不让一个不可能的副本阻断其他可行副本。

首版上限为 16 个唯一分配；超过上限时按照候选收缩程度与已知库存排序，取 16 个最受约束分配，并在日志标记 `suit_resolution="bounded"`。

## 界面与结算检测

对局动态不再使用 HTML 换行、牌面表格和每条事件后的空块。出牌显示为一行：`第 N 手　左家出牌：33445?7`；小王和大王仍显示中文；花色推断只在必要时追加短标签。游次、接风、识别提示和自动封存同样各占一行。

配置一个独立的 `game_end_controls` 区域覆盖底部结算按钮。`recognize_fast_signals` 与 `recognize_opening_signal` 同时扫描普通行动按钮区和结算按钮区并合并去重结果。确认到 `continue_game` 或 `change_table` 后，orchestrator 只发布一次 `game_end_detected`；现有 controller 连接负责异步封存并重启监听。

## 验收标准

- 由真实首手截图构造的左家出牌返回六张，其中遮挡 5 显示为 `5?`，而非删去；两帧共识提交六张动作。
- 把梅花 8 误作黑桃 8 的临时策略分配不会写入 reducer 事实；之后出现真正的黑桃 8 时，只会收缩候选或重算建议，不能产生“第三张黑桃8”而中断回合。
- 含未知花色的动作照常扣减六张，玩家最终剩余牌归零时仍发出 `player_finished`；满足接风条件时仍发出 `wind_caught`。
- 同一批可行花色副本一致时建议为高置信；不一致时建议记录 `ambiguous` 并在 UI 以低置信可见。
- 结算页真实末帧识别到 `continue_game` 或 `change_table`；控制器仅调用一次 `finish()`，manifest 状态为 `sealed`，随后监听恢复。
- UI 对出牌、游次、接风和结算事件均在 `QTextEdit.toPlainText()` 中呈单行紧凑文本。
