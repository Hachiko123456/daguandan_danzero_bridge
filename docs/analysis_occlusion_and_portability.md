## 问题 1：左家出 ≥5 张时花色被遮挡，能否处理

### 1.1 先确认事实：你的观察完全成立，而且是"左家专属"

用仓库内全部历史 session 统计"出牌张数 × 是否出现未知花色（`10?` 这类）"：

| 座位 | 张数 | 事件数 | 含未知花色 | 比例 |
| --- | --- | --- | --- | --- |
| **左家** | **5** | **57** | **27** | **47.4%** |
| **左家** | **6** | **4** | **2** | **50.0%** |
| 左家 | 1–4 | 127 | 1 | 0.8% |
| 右家 | 5 | 40 | 0 | 0.0% |
| 右家 | 6 | 9 | 0 | 0.0% |
| 对家 | 5 | 35 | 1 | 2.9% |
| 自己 | 5–6 | 40 | 0 | 0.0% |

**结论：左家 ≥5 张时约一半的出牌会丢花色；右家同样出 5–6 张却一次都不丢。**
这不是"牌多就遮挡"的普遍规律，而是左家出牌区特有的几何耦合。

### 1.2 遮挡源：不是牌与牌重叠，是游戏自己的 UI 图层

把 4 个 session 中"左家 ≥5 张且含未知花色"的帧从录像里取出来、裁到左家出牌区放大后可以看到两个叠加的机制：

1. **游戏自身的按钮 / 徽章 / 特效图层绘制在左家牌面之上。**
   - 轮到自己时出现的「不出」「提示」按钮、座位等级徽章、牌型特效文字，都位于左家牌列的右下方。
   - 牌列越向右延伸（张数越多），最右 1–2 张牌的中下部（**花色符号所在位置**）就越容易落进这些图层的覆盖范围。
   - **点数在牌的左上角，始终外露**，所以点数能读到、花色读不到——这正是系统写出 `5?`、`A?`、`K?` 而不是整张牌失败的直接原因。
2. **横向排列时牌与牌之间的重叠**，进一步压缩了花色符号的可见面积。

配置层面也印证了这种重叠：`left_play` 为 `x 135..485, y 188..284`，而 `button_actions` 为 `x 450..899, y 210..359`，两者在 `x 450..485 / y 210..284` 直接重叠；`passed_left`（`x 138..257, y 215..284`）更是整个落在 `left_play` 框内。

典型受害牌型（真实样本）：三带二（3+2）里的"带二"、三连对、顺子的最右一张。例如
`('4C','4D','4S','8?','8D')`、`('A?','A?','K?','K?','QD','QS')`、`('2D','2H','2S','3?','3D')`。

证据图见 `reports/left_occlusion_analysis/`。

### 1.3 能否处理：能，而且不必"看清"花色

按性价比从高到低，四层都可以独立落地：

**L1｜把左家出牌区的读取时机前移到"左家自己的回合内"（最高性价比）**
现在左家出牌区主要是在"轮到自己"之后补读（`suit_corrected` 路径），这时按钮已经出现。
但左家的牌在他自己回合就已落位，**那一刻「不出/提示」按钮还不存在**，是干净帧。
项目已经有 `burst_read`、特效门控、"静止窗口"这套采样机制，只要把左家出牌区的采样窗口挂在"左家 action epoch 开始"而不是"轮到自己"，多数遮挡就自然消失。
预期收益最大、改动最小、不动识别算法，是最应该先做的一件事。

**L2｜出牌区拆成「角标区 + 花区」两个子 ROI，分开匹配打分**
当前是整张牌一次匹配，任一部分被覆盖就可能整牌失败，代价太大。
拆开后：角标区（点数）被覆盖的概率低得多，花区不可读时只把花色标 `?`，点数照常提交。
这也让"哪一部分被遮挡"变成可观测信号，而不是一个笼统的匹配失败。

**L3｜遮挡感知门控（把现有的特效门控推广到 UI 遮挡）**
项目已经有 `button_actions`、`passed_*` 区域和按钮模板，能判断按钮在不在。
在读左家出牌区之前，先判断"按钮/特效是否覆盖左家出牌区右下角"：
覆盖 → 本帧只作为点数证据，不作为花色证据，改取更早或更晚的帧。
这与现有"命中牌型特效 → 丢弃突发样本 → 静止 450ms 再读"是同一个模式，属于既有机制的推广，概念上不新增东西。

**L4｜约束推断（项目已具备，只需把候选集收窄）**
`live/card_uncertainty.py` 已经有 `feasible_action_variants`、`state_variants_for_unknown_suits`：
- 双副牌约束（每张确切牌最多 2 张、同点数最多 8 张、同花色最多 26 张）；
- 结合自己手牌 + 已确认历史，把 `10?` 收敛到很少几种可能；
- 多个花色变体一起送给模型，并在结论一致时标记 `advice_agrees_across_variants`。

**可以加的增量**：把 `?` 的候选集从"4 个花色"进一步按**牌型结构**收窄。例如左家出的是三带二 `5? 5D`，另一张 5 已经是 ♦，那么在双副牌约束下 `5?` 的候选立刻减少；再叠加顺子/连对/同花顺的结构约束，候选会急剧收敛。**这比"重新看清花色"更省事、也更稳。**

**L5｜长期：用检测模型替代模板匹配（可选）**
YOLO 一类检测头直接输出"牌 + 花色"的框，对遮挡、缩放、特效的鲁棒性显著优于模板匹配（参考第 2 节的 `Portable-Real-Time-Poker-Assistant`：4 个 YOLOv8-nano 分别做牌/筹码/动作检测，mAP 99%+）。
代价是要标注数据——而本项目已有 30 局录像、104 个模板、`label_status=verified` 的 TruthLog，`application/dataset.py` 已经在按 ROI 导出训练样本。这条路的启动成本比一般项目低。

### 1.4 不建议的三个方向

- **改 `left_play` 的位置 / 大小**：牌本身就画在那里，改框不能把被盖住的像素变回来（换个位置还会切到牌）。
- **缩放或改窗口尺寸**：牌和按钮都是游戏内部布局，一起等比变化，相对遮挡关系不变；而且窗口尺寸在启动时就被强制锁定（见问题 3），本来就改不动。
- **上 OCR**：花色是图形不是文字，OCR 帮不上；项目已明确选择不依赖 OCR，这条路方向相反。

### 1.5 建议先做的一件事：把损失量化

现在 `advice.jsonl` 里已经有 `suit_uncertain`、`suit_variant_count`、`suit_equivalence_class_count`。
建议加一条统计：**有多少条建议因为历史里存在 `?` 而多算了变体、或在不同变体间结论不一致**。
先把这个数字拿出来，再决定 L1–L4 投多少工程——如果左家花色的不确定性几乎不影响最终建议，那它就是个体验问题而不是正确性问题。

### 2.1 同场景（微信小程序 + 模板匹配 + 后台截图）

### 2.2 同游戏（掼蛋 AI 引擎，解决的是"决策"不是"识别"）

- `AltmanD/guandan_mcc`（DanZero 原版，论文 2210.17087）
- `rezeu/GuandanProj`（基于 rlcard 魔改）

这些解决的是推荐/决策。你的 `src/daguandan_bridge/danzero/_vendor/guandan_rlcard` 已经是 rlcard 的 guandan 分支。
**可借鉴的点**：DanKS 的"先做结构化候选检索（有预算的拆牌搜索生成代表性候选），再让策略网络做长期价值判断"两段式设计。

### 2.3 视觉方案升级路线

- `pjgranieri/Portable-Real-Time-Poker-Assistant`：4 个 YOLOv8-nano 分别做牌/筹码/动作检测，多阈值置信度融合 + 自适应 ROI 裁剪 + 帧间 ROI 切换。
  **这是"模板匹配 → 检测模型"的范式**，对遮挡最鲁棒，和问题 1 的 L5 对应。
- `MemDbg/poker-vision`、`c-yanger/Poker-Assistant`：OCR / 轮廓路线。
- `newMeta98/ace-autopilot-poker-ai`：Moondream-2B 视觉模型 + DeepSeek 决策。单张推理 300ms+，对"轮到自己后几秒内要出建议"的节奏太慢，只适合离线复盘。

### 2.4 别人怎么做得稳 vs 你已经做对的地方

**值得直接抄的 5 条工程习惯：**

1. **观测与决策分离**。识别层只产出"候选 + 置信度 + 拒绝理由"，状态层只做事务提交。
2. **一封不可变事实源 + 可重放**。出问题能定位、修完能验证。
3. **帧证据 + 多帧共识 + 时序门控**。两帧一致才提交；特效期间丢帧并等静止窗；按钮消失/重现用边沿检测而不是状态检查。
4. **物理约束兜底**。双副牌上限、同点数最多 8 张、同花色最多 26 张、自己打出的牌必须来自已知手牌。
5. **失败可恢复而不是重开**。出错后从原动作位置原子重放后续状态、`action_id` 不变。

**你已经做到、而开源同类基本没做到的：**
`timeline.jsonl` 不可变事实源、`observations.jsonl.gz` 保留全部候选与拒绝理由、`frame_index.jsonl` 用真实单调时钟而不是播放器 FPS、`visual_replay` 按原始时间戳整局复测、`incidents/` 自动生成 `llm_report.md` + 联系表、TruthLog 保存时的物理牌库校验、`event_correction` 原位修正且不改变 `action_id`。
**在这批同类项目里，你的工程化程度明显更高一层。**

**可以补的一条（与问题 3 直接相关）：**
硬件加速窗口的备用采集后端。`PrintWindow` 对 GPU 渲染的窗口可能返回黑屏（微信小程序尤其常见），业界推荐的绕法是 WGC（Windows Graphics Capture，Win10 1803+），它直接从桌面合成器取帧、绕过渲染层保护。
你现在的 `auto → printwindow → screen / gdi_screen` 可以再加一层 WGC，并把"黑屏"明确归因，而不是笼统的 backend failed。

## 问题 3：监听的是微信小程序窗口，且窗口尺寸改不了

### 3.1 先说一个可能被忽略的硬约束

**窗口尺寸在本项目里不是可选项，而是启动前置条件。**

`gui/live_controller.py::start_listening()` 会先调用
`capture_service.lock_target_client_size()` → `window_capture.resize_target_client()`
用 `SetWindowPos` 把目标窗口**客户区强行调到 `target_client_size = 1280×764`**；
**失败就 `return False`，监听根本起不来**，报错文案是"无法锁定牌桌客户区尺寸：目标窗口未接受请求尺寸：期望 1280x764，实际 …"。

所以：
- 如果你现在**能**正常起监听 → 说明 `SetWindowPos` 对微信小程序窗口是生效的（WeChatAppEx 是普通顶层窗口，通常允许被程序改尺寸），"窗口大小没办法改变"这件事其实不存在。
- 如果你**起不来** → 就是这里挡住的，先解决尺寸锁定，再谈识别。

无论哪种情况，都建议把"目标尺寸"从隐式常量变成可配置项 + 启动自检，失败时给出明确指引，而不是硬失败。

### 3.2 真正与小程序相关的坑是"后台截图黑屏"，不是尺寸

微信小程序用 GPU / WebGL 渲染：`BitBlt` 只能读到屏幕 DC（拿到旧帧或黑屏），**`PrintWindow` + `PW_RENDERFULLCONTENT` 才是正解**。
你的 `capture_client_image_printwindow` 已使用 `0x1 | 0x2`（`PW_CLIENTONLY | PW_RENDERFULLCONTENT`），并且在 `_validate_captured_image` 里对 printwindow 返回全黑做显式拒绝（`CAPTURE-BLACK-FRAME`）。**这两点做对了。**

仍存在的风险点：
1. 微信有"截图时隐藏当前窗口"这类隐私习惯，会让窗口在截屏瞬间消失。
2. 部分驱动 / 微信版本下 `PrintWindow` 依然返回黑屏 → 回退到 `screen` / `gdi_screen` → 而 `screen` 会被你自己的推荐浮窗遮挡 → 遮挡检测拒绝该帧并暂停流程 → **结果就是"浮窗必须放在牌桌外"**，单屏时非常受限。
   建议：加 WGC 后端作为 `PrintWindow` 的替补，并把 `find_screen_occluders` 的遮挡判定从"任何顶层窗口"细化为"实际覆盖牌桌客户区"的窗口，避免误判系统托盘之类。

### 3.3 一个对你有利的既有设计

因为客户区被强制成 1280×764 **物理像素**，且 `dpi.py` 把进程设为 Per-Monitor V2 DPI 感知，所以**采集画面的尺寸不受系统缩放（100%/125%/150%）影响**——这对"换电脑"是很大的加分项。

**但需要在一台 125% / 150% 缩放的机器上实测一件事**：如果目标小程序窗口本身是 DPI-unaware，Windows 会对它做位图拉伸，那么同样 1280×764 客户区里游戏内容的有效分辨率会不同，104 个模板的 ROI 就会整体偏移。
这属于"必须实测才能确认"的项，建议列入换机验收清单。

## 问题 4：架构是否合理，换电脑能否正常跑

### 4.1 架构评价：合理，且工程化程度高

分层清晰：`domain / application / infrastructure / presentation` + `live`（旧）/ `live_v2`（生产）双代并存，模型层 `fabledan` / `danzero` 各自 vendor 上游实现。
`live_v2/architecture.py` 用**白名单强制导入边界**（`MODULE_DEPENDENCY_ALLOWLIST`）+ **单模块 600 行上限**，属于"用测试守住架构"，这在同类项目里很少见。

主要结构风险有两个：
1. **规模**：`src` 下 234 个 Python 模块（`live` 21 个文件、`live_v2` 32 个文件、`application` 54 个文件）。旧 `live` 与新 `live_v2` 并存，虽然文档说明旧编排器只服务历史回放，但双份概念仍会持续消耗维护成本。建议明确写一份"哪些模块已冻结、只允许回放路径调用"的清单，并在 CI 上加一条断言。
2. **`live_v2/types.py` 被文档标注为"兼容外观层、不是新定义的地方"**——这类"弃用但仍在用"的模块最容易失控，值得加注释和工具检查。

### 4.2 换电脑：设计上已经考虑过，且有实际证据

**冻结版（EXE）的数据布局是干净的：**
- 发布目录里的 `data/` 被当作**不可写的资源种子**，首次启动按 `build_id` 原子复制到
  `%LOCALAPPDATA%\DaguandanAssistant\data\v1\generations\<build-id>\data\`；
- 所有可写内容（sessions、截图、模板、模型、日志、诊断、偏好、缓存）都在用户目录，**不写 EXE 所在目录**；
- 复制前后逐文件校验 SHA256，seed 缺失/变化/多出文件都会闭合式失败；
- 迁移 / 回滚用 compare-and-swap 指针 + 本地回执，可安全重复执行；
- `DAGUANDAN_DATA_ROOT` 环境变量可整体替换数据根目录 → 便携部署。
（`runtime_layout.py`，1200+ 行，逻辑相当严谨。）

**实际证据**：`data/profiles/tencent_daguandan/sessions/game_20260918_*` 的 `manifest.json` 里记录的绝对路径是
`C:\project\python_project\daguandan_danzero_bridge\...`，而当前工程在 `D:\project\daguandan_danzero_bridge` ——
说明**这套东西已经在不同盘位（很可能不同机器）上跑过**，session 数据按 profile 相对存放，没有被绝对路径绑死。
唯一的小瑕疵：advisor 的绝对模型路径会被写进 manifest（只是审计元数据，不参与查找），容易让人误判为"路径写死"。

### 4.3 会挡住"换电脑"的 4 个真实风险（按优先级）

**① 对窗口几何的硬耦合（最高）**
客户区被强制 1280×764，104 个模板全部按 1280×720 基准画面标定。
换机器只要那 1280×764 能拿到就一致；拿不到（显示器比 1280 窄、小程序窗口有最小/最大尺寸限制、多屏缩放不同）就直接起不来。
→ 建议：目标尺寸可配置化 + 启动自检 + 明确指引。

**② 模板库是逐像素级的隐式约定**
`templates/` 下 104 个模板是在当前这台机器 / 这个微信版本 / 这个游戏版本上裁出来的。
换机器若微信渲染有细微差别（字体平滑、抗锯齿、缩放），`min_confidence=0.76`、`min_margin=0.04` 可能不再够用。
→ 建议：做一键"新机器标定/自检"流程——用已有的 `table_anchor_*` 锚点匹配 + 全模板自检跑一帧，输出置信度报告，低于阈值直接提示需要重新采集。

**③ 依赖与模型体积**
`torch==2.13.0` 只被 DanZero 用；FableDan 走 numpy 后端（`best.npz`，15.3MB）；`models/` 下也**没有** `danzero/q_network.ckpt`，说明 DanZero 权重本来就没随包走。
→ 建议：**如果不打算用 DanZero，把 `torch` / `rlcard` 从必需依赖里摘出去**。torch 在无网或受限网络环境下是"换电脑装不上"最大的失败点。发布流程已经是离线 wheelhouse + 哈希锁定，方向是对的，把非必需重依赖移出去会明显降低换机成本。

**④ `base_size` / `target_client_size` / `viewport_mode` 三者的组合语义容易踩**
当前是：`base_size = 1280×720` + `viewport_mode = bottom_aspect` + `viewport_aspect_ratio = 16/9` + `target_client_size = 1280×764`
→ 即"把客户区撑到 1280×764，再取顶部 1280×720 当游戏画面"。
换了微信版本如果底部控件高度变了，这 44px 的差值就可能失效。
→ 建议：启动时**校验实际捕获画面里锚点的匹配位置**，而不是信任固定偏移。

## 结论与建议执行顺序

| 优先级 | 事项 | 说明 |
| --- | --- | --- |
| P0 | 确认监听能否正常启动 | 若被"无法锁定牌桌客户区尺寸"挡住，先解决这个，其他都无从谈起 |
| P0 | 左家出牌区读取时机前移到左家回合内（L1） | 性价比最高，不动识别算法，预计消除大部分 `?` |
| P1 | 出牌区拆「角标区 + 花区」子 ROI（L2） | 让遮挡变成可观测信号，而不是整牌失败 |
| P1 | 量化 `?` 对建议的实际损失 | 用 `advice.jsonl` 已有的 `suit_*` 字段统计，决定后续投入 |
| P1 | 换机自检流程（锚点 + 全模板置信度报告） | 解决风险 ①②④ |
| P2 | 遮挡感知门控（L3） | 复用现有特效门控模式 |
| P2 | `?` 候选集按牌型结构收窄（L4） | 复用 `card_uncertainty.py` 已有枚举 |
| P2 | 加 WGC 采集后端 | 解决小程序 GPU 渲染黑屏导致的 `screen` 回退受限 |
| P2 | 非必需重依赖剥离（torch / rlcard 可选化） | 解决风险 ③ |
| P3 | 用检测模型替代模板匹配（L5） | 长期方向，本项目标注数据成本低于同类 |
